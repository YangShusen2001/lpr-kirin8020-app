# C2（NV21→RGBA 分块转置）—— 否定结果

**结论：分块转置没有加速。conv p50 从 6.31/8.38 ms 变为 7.45 ms，落在既有波动区间内。**

## 假设与其被推翻的过程

假设：`rot=90` 时目标行号 `dy = x` 随内层循环的 `x` 递增，于是每写 4 字节
就换一条新缓存行（写利用率 4/64），30 万像素 = 19.6 MB 无效写流量。
按 16×16 源块分块应把写侧变成 64 字节连续、读侧也被块内 x 循环复用。

**这个假设错了。** 证据是 `conv min`：

| | 改前 sweep1 | 改前 sweep2 | 改后 sweep3 |
|---|---|---|---|
| conv min | 2.19 | 2.18 | **2.10** |
| conv p50 | 6.31 | 8.38 | **7.45** |

`min` 近似"未受降频干扰时的算法成本"。它从 2.19 只动到 2.10（约 4%），
说明**真实工作量并没有下降** —— 若散射写真是主因，min 应该成倍下降。
所以缓存行散射不是瓶颈，编译器/硬件大概已经把这件事处理掉了。

## 为什么 p50 仍然 6~8 ms，而 min 只有 2.1 ms

conv 的动态范围是 **2.1 ~ 14.7 ms（约 7 倍）**，稳态后依然如此
（`camera_sweep1.log`：稳态后 min=2.19 p10=3.01 p50=6.31 p90=10.05 max=13.63）。
这个跨度不可能来自算法本身，和 C8 的结论一致：

- conv 是 `g_runner` 专用线程被 `cv_.wait()` 唤醒后的**第一件工作**，
  它的耗时取决于唤醒时 CPU 处在什么频率/什么调度状态；
- p50 与 min 的 3 倍差，是**线程唤醒 + DVFS** 的代价，不是转换循环的代价。

因此 **conv 的 p50 不是算法指标**，它主要是一个调度指标。这也解释了为什么
优化算法对它无效 —— 我们优化的是只占 min 的那部分。

## 纪律意义

1. **min 是判断"工作量"的探针，p50 是判断"到达成本"的探针。** 两者差 3 倍
   时，任何针对工作量的优化都只能在 min 上显形。以后先分离这两个量，
   再决定动不动手。（对应纪律 7：隔离 ≠ 流水线。）
2. **用 min 做零假设检验**：若优化有效，min 必须下降。min 不动 → 工作量没变
   → p50 的变化只是噪声。这一条成本极低，应在每次 CPU 侧优化前先跑。
3. 顺带修正一处**聚合错误**：此前我用「p50 相减」算 det 段闭合缺口（得 1.50 ms），
   正确做法是「逐帧相减再取 p50」（得 0.85 ms）。差值的 p50 ≠ p50 的差值。

## 副作用（保留）

改动本身是安全的：16 组尺寸/stride/旋转角上**逐字节相等**
（`tools/verify_nv21_to_rgba.py`，含手算坐标映射校验），且抽出了
`Nv21PixelToRgb()` 让两条路径共用同一份算术。**代码保留**，不因无收益而回滚 ——
它已证明等价，且为后续可能的 SIMD 化铺好了结构。

同时记录一个**潜伏越界读**：奇数 stride 时色度会多读 1 字节
（`uvRow[(x/2)*2 + 1]` 越过 `ySize + stride*uvRows`）。相机给 stride=640（偶），
线上不触发。守卫里以「记录、不判失败」的形式固定下来，未随本次改动一并修。
