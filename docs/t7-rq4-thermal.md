# T7 · RQ4 持续负载热特性

- **日期**：2026-09-21
- **票**：#8
- **对应 ADR**：ADR-0007（范围收口 RQ3+RQ4）
- **数据**：`evidence/rq4_thermal.csv` / `.json`（**20 轮，0 破例**）
- **设备日志**：`evidence/rq4_thermal_device.log`（已过滤，仅含探针相关行）

> **数据在修复后的构建上重采。** 此前那版 `LprEncodePlateInto` 的 padding 未清零，
> 导致识别输入张量被污染（`code=苏ED512`、`rec.l2=3.0965`）。本轮重采后

## 方法

连续跑生产档流水线（`det=CPU / rec=NNRT / cls=CPU`），每 15 s 一轮，逐轮记录：

| 字段 | 来源 | 说明 |
|---|---|---|
| `thermal` | `thermal.getThermalLevel()` | 0=COOL … 5=EMERGENCY |
| `battC` | `batteryInfo.batteryTemperature` | 单位为 **0.1 ℃**，已除以 10 |
| `soc` / `chg` | `batteryInfo` | 电量 / 充电状态 |
| `load` | `systemLoad.getLevel()` | 系统负载档 |
| `totalMs` | 流水线返回 | 端到端延迟 |
| `backends` | 流水线返回 | **落点自证**（含 det/rec 的 `l2` 张量指纹） |
| `p0` | 流水线返回 | 完整车牌明细（chars / cropSum / 分段） |

热态数据**只能在 ArkTS 侧取** —— native sysroot 里没有热态头文件
（已查 `native/sysroot/usr/include`，无 `thermal*`）。三个 API 都在
`openharmony/ets/api/` 下，不在 `hms/ets/api/`。

### 轮间方差：按 CPU / NPU 分开报

票面验收明确要求「轮间方差按 CPU / NPU 分开报告（不合并成一个数字）」。做法是按
**后端归属**拆 `p0` 里的 9 个分段时延（顺序见 `napi_init.cpp:776`）：

| 侧 | 组成分段 | n | mean | stdev | **CV** | min | max |
|---|---|---|---|---|---|---|---|
| **CPU 侧** | `tDetectMs`+`tRectifyMs`+`tClsMs` | 20 | 101.19 ms | 21.10 | **20.8%** | 56.69 | 137.43 |
| **NPU 侧** | `tRecogMs` | 20 | 38.80 ms | 5.13 | **13.2%** | 27.99 | 45.12 |
| 端到端（合并） | —— | 20 | 141.03 ms | 22.91 | 16.2% | 86.65 | 180.42 |

**合并后的 16.2% 落在两侧之间，掩盖了「CPU 侧方差大于 NPU 侧」这件事。**
这正是票面禁止合并成一个数字的原因。

逐分段 CV（同一批 20 轮）：

| 分段 | mean (ms) | CV | 归属 |
|---|---|---|---|
| `letterbox` | 39.76 | **51.7%** | CPU |
| `infer` | 37.04 | 40.1% | **CPU**（生产档 det 在 CPU 上） |
| `encInfer` | 38.91 | 37.8% | CPU |
| `pack` | 1.88 | 26.1% | CPU |
| `detect`（整段） | 82.15 | 25.2% | CPU |
| `decNms` | 0.11 | 15.5% | CPU |
| `rectify` | 18.45 | 14.3% | CPU |
| `recog` | 38.80 | **13.2%** | **NPU** |
| `cls` | 0.60 | 12.1% | CPU |

**最大的方差源仍是 `letterbox`（CV 51.7%）—— 一段纯 CPU 的缩放/填充，不含任何推理。**
一个纯内存搬运的方差超过所有推理段，说明这轮波动的驱动因素是
**CPU 调度与频率，不是算力或热降频**。

**完整性校验**（证明分列没有漏掉时间）：`detect` 是**整段**（已含
`letterbox`/`pack`/`infer`/`decNms`），故顶层分解只能是
`detect + rectify + recog + cls`。实测四段之和与端到端之间：

```
未计入残差: mean = 1.03 ms  (min 0.85 / max 1.45)  = 端到端的 0.73%
```

残差约 1 ms 且稳定（应为流水线外的计时收尾开销），故 **CPU/NPU 分列覆盖了
几乎全部耗时**，不是「只统计了一部分」。

> ⚠️ **归属是近似的，不是设备内核时间。** `tRecogMs` 里仍含 NNRT 的 host 侧
> 前后处理，故 NPU 侧的 13.2% 是「调用 NPU 的那一段」的方差，不是 NPU 内核的方差。
> 与 `ShusenPaper` 既有的「NPU 端 <8%」**不可直接相比**（那是在 L2 套件、
> 不同模型与协议下测的）。此处只做**与本实验 CPU 侧的同栈对照**。

### 三条结论

**① 热态在 5 分钟内完全没有爬升。**

`thermal` 全程恒定 **2**（WARM），电池温度在 **35.0–36.0 ℃** 之间抖动
（幅度 1 ℃，即 10 个 0.1 ℃ 单位，且是**下降**而非上升）。系统负载档
`load` 恒为 **2**，SOC 恒 **100**（充电中 `chg=3`）。
**没有跨过 thermal 2→3 的台阶**，因此既有的
「thermal 2→3 时 NPU 延迟 +15~20%」那条规律**在本实验中未被触发**。

**② 落点自证指纹逐轮恒定 —— 后端行为稳定。**

```
det.l2 = 1076.7692   （20 轮 1 个不同值）
rec.l2 =  4.0489     （20 轮 1 个不同值）
code   = 苏ED5172     （20 轮 1 个不同值，7 字符合法）
```

这比延迟数字更硬：**张量指纹不变意味着 NPU 上的计算路径没有退化**。
延迟的抖动（87→180 ms）**不是**热降频引起的，因为指纹没动。
本轮 0 破例（上一版有 1 轮 `ok!=1`，那是被污染的旧构建）。

**③ 延迟波动 16.2% 的主因不是热态，而且大部分来自 CPU 侧。**

热档恒定、指纹恒定，而延迟在 87–180 ms 之间摆动 → **波动来自热态以外的因素**
（调度、CPU 频率、后台干扰）。这与 `ShusenPaper` 既有的
「CPU 端轮间方差 30–50%、NPU 端 <8%」自洽：生产档的 det 在 **CPU** 上，
而 CPU 端正是方差大的那一侧。

分列后这一点更清楚：**CPU 侧 CV 20.8%，NPU 侧 CV 13.2%**（见上节）。
且单段方差最大的 `letterbox`（CV 51.7%）**完全不含推理** —— 它只是缩放与填充。
一个纯内存操作的方差超过任何推理段，说明这轮波动的驱动因素是
**CPU 调度与频率，不是算力或热降频**。

## 一个真实的记录缺陷（本轮发现并已修）

首版 RQ4 日志**只记 `code`，不记完整 `p0`**。当发现识别结果与既有基线不一致时，
**无法自查**（`cropSum` 与分段明细正是为这种跨会话对照准备的）。

修法：`p0` 单独成行（`RQ4P r=N p0=...`）—— 它与主行拼在一起会被 hilog 的单行
上限截断，单独成行才能完整落盘。

## 限制（引用时必须一起说）

- **只跑到 thermal=2，未触发 thermal≥3。** 所以本实验**没有测到**降频台阶；
  要测它需要更长的负载或更高的环境温度。既有「2→3 时 NPU +15~20%」的结论
  **既不因此被证实也不被证伪**。
- **只有 5 分钟 / 20 轮、单一会话、单机，且充电中（`chg=3`、SOC 恒 100）。**
  充电会带来额外热源，也会让系统更倾向保持性能档 —— 这与电池供电下的
  热行为**可能不同**。协议要求的 ≥5 轮是跨会话的，本轮是**单会话 20 点**，
  不等价于 5 轮。
- **CPU / NPU 分列是按阶段归属的近似**，不是设备内核时间：`tRecogMs` 含 NNRT 的
  host 侧前后处理。故 NPU 侧 CV 13.2% 只可与**本实验的 CPU 侧**对照，
  不可与 `ShusenPaper` 的「NPU 端 <8%」直接相比（不同模型/协议）。
- **无 Fisher-Yates 洗牌**（本探针只跑一个模型，无顺序可洗）。
- **未记录环境温度**，只有电池温度。
- 探针默认时长 20 分钟（80 轮），本次**按用户要求提前在 20 轮（5 分钟）停止**。

## 附：一个真实缺陷的定位与修复（原登记为「未定位异常」）

**同一输入、同一模型，识别结果会随会话历史变化。根因已定位：是我自己代码里的
输入张量 padding 未清零，由 NHWC/NCHW 两条布局共享同一块 scratch 触发。**

### 现象

| 时机 | `code` | 字符数 | rec.l2 | l2AsFp16 | used |
|---|---|---|---|---|---|
| 全新进程、ncnn 槽位加载**前** | `苏ED5172` | 7 ✓ | **4.0489** | 3692.1536 | 1 |
| ncnn 槽位加载**后**（即使走回 MS） | `苏ED512` | **6 ✗** | **3.0965** | 4521.9430 | 1 |

同一 `cropSum=2773473`（同一输入）、同一 `.ms`（SHA256 三份相同）、同一
`NNRT:NPU_ohos...kirin8020_v2_0` 落点。**6 字符长度非法**（合法为 7/8）。

### 定位过程（可复现）

关键是把**一次进程会话**内的完整时间线对齐（`tools/parse_rq4.py` 只处理热特性，
此处的分析脚本在 `~/lpr-data/timeline_repro.py`）：

```
02:45:19–25  mode=ms    code=苏ED5172  l2=4.0489   ← 全新进程，缓冲全 0
02:45:26.247 ncnnLoadSlot slot=1                  ← ncnn 首次加载
02:45:26.449 mode=ncnn  code=苏ED512              ← NCHW 写满整块缓冲
02:45:29.061 mode=ms    code=苏ED512  l2=3.0965   ← 切回 MS，读到被污染的输入
```

**决定性一步**：把 App 强停再启动（清空 `thread_local` scratch），启动阶段 MS
稳定给 `苏ED5172`；一跑「三后端槽位」探针就变 `苏ED512`。**同一进程内可复现，
重启即恢复** —— 这排除了模型、固件、NPU 的一切解释。

### 根因

`LprEncodePlateInto`（`lpr_pipeline.cpp:768`）对 crop `123×78` 算出
`targetW=160`、`resizedW=76`，随后：

```cpp
out.resize(3 * plane);          // ← 只有当元素数变大时才值初始化
for (y...) for (x < resizedW...) { ... }   // 只写 x ∈ [0,76)
```

**列 `[76, 160)` 从不写入。** 而参照实现是
`padding_im = np.zeros((imgC,imgH,imgW))` 后只填 `[:, :, 0:resized_w]`
（`hlpr_reference.py:178`）—— **padding 恒为 0**。

由于 `targetW` 固定在 `[48,160]`、crop 尺寸也固定，`resize()` 几乎总是空操作，
于是 padding 列保留**上一次调用**的值。而 NHWC 与 NCHW 写的是**不同的下标集合**
（NHWC `(y*W+x)*3+c` vs NCHW `c*plane + y*W+x`），所以空洞里留下的是
**另一种布局的残值**，不是「上一次同一位置的值」。

生产档 `det=CPU / rec=NNRT` 本来不该互相影响，但只要中间跑过一次 ncnn 槽位
（NCHW，写满整块），随后 MS(NHWC) 就会读到被 NCHW 残值污染的输入张量。

### 修复

```cpp
out.assign(3 * plane, 0.0f);    // 显式清零，对齐参照的 np.zeros
```

### 验证

**一、数值层面**（对照 Python 参照实现，`~/lpr-data/verify_padding_fix.py`）：

```
crop 123x78 -> resizedW=76, targetW=160   padding 列 = [76, 160)

修复前 resize(): padding 区 max|v|=0.5000  全为 0? False
修复后 assign(): padding 区 max|v|=0.0000  全为 0? True
参照实现的对应量:  padding 区 max|v|=0.0000  全为 0? True
```

修复后 padding 区与参照**同样恒为 0**。

**二、真机层面**（同一操作序列：启动 → 自动探针跑完 → 点样本 1）：

| | ncnn 槽位加载后走 MS |
|---|---|
| 修复前 | `苏ED512` / `l2=3.0965`（**稳定复现**） |
| 修复后 | `苏ED5172` / `l2=4.0489`（**全程稳定**） |

修复后连跑「三后端槽位」探针（含 rec/cls 各 CPU+Vulkan 四组加载），
后续 MS 输出**始终** `苏ED5172`、`l2` 始终 `4.0489`；`used=0` 的 ncnn 行
也给 `苏ED5172`，说明两条布局都不再被对方污染。

**三、重采 T7 数据**：修复后重跑 20 轮 RQ4，`code` 与 `rec.l2` **各只有 1 个值**、
0 破例（旧构建下 `rec.l2` 有 2 个值）。本文档的结果已全部换成这一版。

### 这条缺陷对论文主张的意义

**它反过来验证了 ADR-0003 的落点自证确实有效**：一个纯前处理的 padding 缺陷，
在**输出层不可见**（车牌串看着像模像样，只是少一个字符），却被
`l2` / `l2AsFp16` 这组**张量指纹**忠实记录了下来 —— 两个状态各自稳定，
指纹随之分成两簇。

**同时它划出了落点方法的边界**：指纹能证明「输入/输出变了」，但**不能区分**
「NPU 行为变了」与「我喂给它的张量变了」。本轮的 `l2=3.0965` 一度被读成
「NPU 前后两次会话给出不同结果」，直到把会话时间线与槽位加载对齐才定位到
**是输入侧的问题**。引用指纹异常时，必须先排除自己这一侧的输入变化。
