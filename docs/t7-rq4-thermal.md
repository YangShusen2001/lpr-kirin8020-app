# T7 · RQ4 持续负载热特性

- **日期**：2026-09-21
- **票**：#8
- **对应 ADR**：ADR-0007（范围收口 RQ3+RQ4）
- **数据**：`rq4_thermal.csv` / `rq4_thermal.json`（16 轮，15 有效 + 1 破例）

## 方法

连续跑生产档流水线（`det=CPU / rec=NNRT / cls=CPU`），每 15 s 一轮，逐轮记录：

| 字段 | 来源 | 说明 |
|---|---|---|
| `thermal` | `thermal.getThermalLevel()` | 0=COOL … 5=EMERGENCY |
| `battC` | `batteryInfo.batteryTemperature` | 单位为 **0.1 ℃**，已除以 10 |
| `soc` / `chg` | `batteryInfo` | 电量 / 充电状态 |
| `load` | `systemLoad.getLevel()` | 系统负载档 |
| `totalMs` | 流水线返回 | 端到端延迟 |
| `backends` | 流水线返回 | **落点自证**（含 det/rec 的 `l2` 张量指纹） |
| `p0` | 流水线返回 | 完整车牌明细（chars / cropSum / 分段） |

热态数据**只能在 ArkTS 侧取** —— native sysroot 里没有热态头文件
（已查 `native/sysroot/usr/include`，无 `thermal*`）。三个 API 都在
`openharmony/ets/api/` 下，不在 `hms/ets/api/`。

### 轮间方差：按 CPU / NPU 分开报

票面验收明确要求「轮间方差按 CPU / NPU 分开报告（不合并成一个数字）」。做法是按
**后端归属**拆 `p0` 里的 9 个分段时延（顺序见 `napi_init.cpp:776`）：

| 侧 | 组成分段 | n | mean | stdev | **CV** | min | max |
|---|---|---|---|---|---|---|---|
| **CPU 侧** | `tDetectMs`+`tRectifyMs`+`tClsMs` | 15 | 109.17 ms | 32.75 | **30.0%** | 66.81 | 172.33 |
| **NPU 侧** | `tRecogMs` | 15 | 35.87 ms | 6.54 | **18.2%** | 19.15 | 43.78 |
| 端到端（合并） | —— | 15 | 146.01 ms | 32.92 | 22.5% | 86.98 | 208.24 |

**合并后的 22.5% 恰好落在两侧之间，掩盖了「CPU 侧方差显著大于 NPU 侧」这件事。**
这正是票面禁止合并成一个数字的原因。

逐分段 CV（同一批 15 轮）：

| 分段 | mean (ms) | CV | 归属 |
|---|---|---|---|
| `letterbox` | 43.07 | **61.6%** | CPU |
| `decNms` | 0.13 | 46.7% | CPU |
| `infer` | 40.19 | 45.1% | **CPU**（生产档 det 在 CPU 上） |
| `encInfer` | 42.11 | 42.7% | CPU |
| `detect`（整段） | 89.46 | 32.9% | CPU |
| `rectify` | 19.13 | 28.3% | CPU |
| `pack` | 1.92 | 23.9% | CPU |
| `recog` | 35.87 | **18.2%** | **NPU** |
| `cls` | 0.59 | 12.1% | CPU |

**最大的方差源是 `letterbox`（CV 61.6%）—— 一段纯 CPU 的缩放/填充，不含任何推理。**
这是「方差来自调度而非算力」的直接证据。

> ⚠️ **归属是近似的，不是设备内核时间。** `tRecogMs` 里仍含 NNRT 的 host 侧
> 前后处理，故 NPU 侧的 18.2% 是「调用 NPU 的那一段」的方差，不是 NPU 内核的方差。
> 与 `ShusenPaper` 既有的「NPU 端 <8%」**不可直接相比**（那是在 L2 套件、
> 不同模型与协议下测的）。此处只做**与本实验 CPU 侧的同栈对照**。

### 三条结论

**① 热态在 4 分钟内完全没有爬升。**

`thermal` 全程恒定 **2**（WARM），电池温度在 **36.0–37.0 ℃** 之间抖动（幅度 1 ℃，
即 10 个 0.1 ℃ 单位）。**没有跨过 thermal 2→3 的台阶**，因此既有的
「thermal 2→3 时 NPU 延迟 +15~20%」那条规律**在本实验中未被触发**。

**② 落点自证指纹逐轮恒定 —— 后端行为稳定。**

```
det.l2 = 1076.7692   （16 轮 1 个不同值）
rec.l2 =  3.0965     （16 轮 1 个不同值）
```

这比延迟数字更硬：**张量指纹不变意味着 NPU 上的计算路径没有退化**。
延迟的抖动（87→208 ms）**不是**热降频引起的，因为指纹没动。

**③ 延迟波动 22.5% 的主因不是热态，而且绝大部分来自 CPU 侧。**

热档恒定、指纹恒定，而延迟在 87–208 ms 之间摆动 → **波动来自热态以外的因素**
（调度、CPU 频率、后台干扰）。这与 `ShusenPaper` 既有的
「CPU 端轮间方差 30–50%、NPU 端 <8%」自洽：生产档的 det 在 **CPU** 上，
而 CPU 端正是方差大的那一侧。

分列后这一点更清楚：**CPU 侧 CV 30.0%，NPU 侧 CV 18.2%**（见上节）。
且单段方差最大的 `letterbox`（CV 61.6%）**完全不含推理** —— 它只是缩放与填充。
一个纯内存操作的方差超过任何推理段，说明这轮波动的驱动因素是
**CPU 调度与频率，不是算力或热降频**。

## 一个真实的记录缺陷（本轮发现并已修）

首版 RQ4 日志**只记 `code`，不记完整 `p0`**。当发现识别结果与既有基线不一致时，
**无法自查**（`cropSum` 与分段明细正是为这种跨会话对照准备的）。

修法：`p0` 单独成行（`RQ4P r=N p0=...`）—— 它与主行拼在一起会被 hilog 的单行
上限截断，单独成行才能完整落盘。

## 限制（引用时必须一起说）

- **只跑到 thermal=2，未触发 thermal≥3。** 所以本实验**没有测到**降频台阶；
  要测它需要更长的负载或更高的环境温度。既有「2→3 时 NPU +15~20%」的结论
  **既不因此被证实也不被证伪**。
- **CPU / NPU 分列是按阶段归属的近似**，不是设备内核时间：`tRecogMs` 含 NNRT 的
  host 侧前后处理。故 NPU 侧 CV 18.2% 只可与**本实验的 CPU 侧**对照，
  不可与 `ShusenPaper` 的「NPU 端 <8%」直接相比（不同模型/协议）。
- **只有 15 个有效点、单一会话、单机**。协议要求的 ≥5 轮是跨会话的，本轮是
  **单会话 16 点**，不等价于 5 轮。
- **无 Fisher-Yates 洗牌**（本探针只跑一个模型，无顺序可洗）。
- **未记录环境温度**，只有电池温度。
- 1 轮破例（`ok!=1`，返回空结果）—— **如实保留未剔除**，见下。

## 附：本轮发现但未定位的一个真实异常

**同一输入、同一模型，识别结果与既有基线不一致。**

| 时机 | `code` | rec.l2 | cropSum |
|---|---|---|---|
| 2026-09-21 01:36（T8 前） | `苏ED5172` | **4.0489** | 2773473 |
| 2026-09-21 02:0x 起 | `苏ED512` | **3.0965** | 2773473 |

**已排除的因素**（逐条实测）：

- 输入不同 → **否**：`cropSum` 逐位相同（2773473），检测框 `1751|747|1879|855` 与
  裁剪尺寸 `78|123` 也相同
- 模型文件不同 → **否**：`rpv3_mdict_160_r3.ms` 的 SHA256 在新旧工程与转换产物间
  **三份完全相同**
- 后端档位不同 → **否**：两次都是 `nnrt`（非 `nnrt_fp32`），落点均为
  `NNRT:NPU_ohos...kirin8020_v2_0`
- 我的 T8 改动 → **否**：检出 T8 之前的 C++（`ca034a5`）重构建，结果**仍是
  `苏ED512` / `3.0965`**
- 输出不确定 → **否**：连点 3 次 + 16 轮循环，结果**逐位稳定**

**结论**：这是一个**可复现的、与本次代码改动无关的差异**。同一个 `.ms` 在 NPU 上
前后两次会话给出不同结果，且各自的指纹稳定 —— 这本身是一条值得追的线索
（NPU 编译缓存？固件状态？），但**不影响 T7 的热特性结论**，因为那部分靠的是
「热档恒定 + 指纹恒定」，不依赖具体的车牌串。

**未做**：定位该差异的根因。需要一次专门的对照实验（冷启动 vs 热启动、
同会话内重复加载等）。
